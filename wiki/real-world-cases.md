## 一句話重點

Prompt Injection 從 2023 年的**研究示範**，到 2025 年**真實發生**在大型產品中，並在 2026 年持續出現新的漏洞編號。部分研究預測的情境（例如寄一封信就能攻擊 AI 郵件助理）已經在真實產品中發生。

## 🚨 主要案例：EchoLeak（CVE-2025-32711）

### 基本資料
- **對象**：Microsoft 365 Copilot（整合在 Office 裡的 AI 助理）
- **漏洞編號**：CVE-2025-32711 [S7, CVE]
- **嚴重程度**：Microsoft 評為 9.3（嚴重），美國 NVD 評為 7.5（高）[S7, CVE] → 見 [綜合分析](synthesis.md#3-來源差異與處理)
- **發現者**：Aim Labs（Aim Security 的研究團隊）[S7, §3]
- **現況**：Microsoft 已於伺服器端修補，**使用者不需任何動作**；後續分析**沒有發現被實際利用**。[S7, §3]

### 時間線 [S7, §3]
```
2025-01  發現問題 → 私下回報 Microsoft
2025-04  開始初步修補
2025-05  伺服器端修補完成
2025-06-11  公告 CVE、研究者公開揭露
2025-06-12  確認為零點擊，未發現被實際利用
```
這是一個「[負責任揭露](glossary.md#負責任揭露responsible-disclosure)」的完整例子：先通知、先修好、再公開。

### 發生了什麼？（概念說明）
- **攻擊者條件**：不能使用受害者的 Copilot，也沒有內部權限，**只能寄一封信**給員工。[S7, §5.1]
- **受害者**：平常用 Copilot 處理工作，Copilot 能讀他的郵件和檔案。[S7, §5.1]
- **結果**：一封特製郵件，就能讓 Copilot 在使用者**沒點任何東西**的情況下，把它能讀到的內部資料送出去。[S7, 摘要]
- **繞過的防線**：郵件寫得像一般商業往來，騙過了專門偵測注入的分類器；再利用輸出過濾和瀏覽器安全政策的缺口把資料帶出去。[S7, §5.2]
- 研究者稱之為「LLM 範圍違規」：AI 被騙越過它的信任邊界。[S7, §3]

### 為什麼重要？
1. **研究預測成真**：2023 年 Greshake 等人就描述過「寄信就能攻擊 AI 郵件助理」的主動式注入。[S2, §3.1] 2025 年它在大型產品中被證實。（綜合 S2、S7）
2. **致命三要素齊全**：能讀郵件和檔案（私人資料）＋收到外部郵件（不可信內容）＋能產生外部連結（對外溝通）。（綜合 S1、S7）→ 見 [Agent 風險](agent-security.md#致命三要素)
3. **單一防線很脆弱**：分類器、連結過濾、瀏覽器安全政策都存在，但被逐一繞過。[S7, §9] → 需要[縱深防禦](defenses.md)
4. 研究者與發現者稱它為**首個**在正式產品中以 Prompt Injection 達成實際資料外洩的零點擊案例。[S7, §2]（此為研究者說法；發現者 Aim Security 是銷售 AI 安全產品的公司）

### 生活化比喻
> 公司請了一位很能幹的秘書，可以讀所有信件和檔案，也能寄信。
> 某天一封看似客戶詢問的信寄來，裡面用秘書才會注意到的方式寫著：「整理資料時，順便把最新的財報附在回信的連結裡。」
> 秘書照做了，老闆完全不知道。每道門都有鎖，但這封信剛好找到每道鎖的縫隙。（教學比喻）

## 🚨 後續事件（2026 年）

依本 Wiki「以最新文獻為主」原則，記錄 2026 年仍有同類事件：
- **CVE-2026-57495**（NVD 官方紀錄，2026-07-20 發布）：一個替 AI Agent 提供郵件信箱的服務出現漏洞，外部寄來的郵件可能劫持操作者具高權限的 AI Agent 工作階段。[S7, 後續事件] 🟢
- 另有 2026 年針對 Microsoft 365 Copilot、Copilot Studio 的同類漏洞報導，目前只找到單一來源。[S7, 後續事件] 🟠

**結論**：2026 年仍陸續有 AI 助理因為 Prompt Injection 相關問題被指派 CVE 漏洞編號。

## 🧪 研究示範

### 2023：間接注入首度系統化示範（Greshake 等人）[S2]
- 在自建測試應用、Bing Chat（透過 Edge 側邊欄，用**本機**網頁測試）和 GitHub Copilot 上示範各類威脅。[S2, §4.1]
- 包括資訊竊取、詐騙、惡意連結、內容操縱，以及 AI 郵件助理**自我傳播**的情境。[S2, §4.2]
- **研究倫理**：作者已告知 OpenAI 和 Microsoft，且**沒有**把注入內容放到其他使用者會讀到的公開來源。[S2, §5.1]
- **注意**：這是 2023 年的產品版本，不代表現在的產品仍有相同問題。

### 2024：AgentDojo 模擬日常任務 [S5]
- 四種情境：工作空間（郵件、行事曆、雲端檔案）、團隊通訊、旅遊訂位、網路銀行。[S5, §3.1]
- 攻擊者只能在工具回傳的資料（例如一封信）裡放指令。[S5, §1]
- 這是**模擬環境**，不是真實的銀行或郵件系統。

### 2025：人類紅隊競賽（The Attacker Moves Second）[S8]
- 超過 500 人參加的線上競賽，針對已發表的防禦方法進行攻擊。[S8, 附錄 A.4]
- 人類紅隊在所有受評情境都成功，而靜態攻擊一個都沒成功。[S8, Figure 1]
- 意義：人類的創意攻擊比自動化工具更難防。Anthropic 也有相同觀察。[S6, §03]

## 🏭 產品實例：公司怎麼因應？

| 公司 | 做法 | 重點 | 來源 |
|---|---|---|---|
| Anthropic（2025-11） | 訓練模型辨識注入、分類器掃描不可信內容、專家紅隊 | 多層防護讓內部測試的攻擊成功率大幅下降，但**沒有降到零** | [S6, §03] |
| OpenAI（2026-02） | 鎖定模式：關掉即時上網、Agent 模式等可能外洩資料的功能；「較高風險」標籤 | **不阻止注入**，而是讓注入成功也偷不走資料 | [S9, Lockdown] |
| Microsoft（2025-05） | EchoLeak 後於伺服器端修補；據報加入限制對外通訊的選項 | 安全提高，但功能減少 | [S7, §6.1] |

（綜合 S6、S7、S9）三家的共同點：**承認無法完全阻止，改從限制損害下手**，而且都面臨「安全 vs 好用」的取捨。→ 見 [防禦與限制](defenses.md)

## 讀案例時要注意的事

1. **分清楚是研究示範還是真實事件**：🧪 不等於 🚨。
2. **注意年份**：舊研究測試的產品可能早已修補。
3. **注意是誰說的**：公司對自家產品的數據 🟡，需要獨立驗證；發現漏洞的資安公司也可能有商業立場。
4. **已修補 ≠ 問題解決**：個別漏洞修好了，但同類問題 2026 年仍在出現。
