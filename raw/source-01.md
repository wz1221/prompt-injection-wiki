## 2026 版排名（前 10 名）

LLM01 Prompt Injection／LLM02 Sensitive Information Disclosure／**LLM03 Excessive Agency**（過度授權，2025 版為第 6）／LLM04 Supply Chain／LLM05 Data and Model Poisoning／LLM06 Unbounded Consumption／LLM07 Misinformation／**LLM08 Hidden Context Exposure**（2025 版 System Prompt Leakage 擴大改名）／LLM09 Vector and Embedding Weaknesses／LLM10 Improper Output Handling

→ Prompt Injection 仍是第一名；「過度授權」升到第三，反映 Agent 風險受重視。

## 重要結論

1. **定義**：輸入讓模型行為以開發者沒有預期的方式改變；輸入可以是使用者訊息、讀取的內容、工具輸出、圖片／聲音／影片、中間推理，或**長期記憶**。[S1, 描述]
   - 與 2025 版相比：2025 版寫的是「使用者提示」改變行為 [S1-2025, 描述]；2026 版把範圍明確擴大到所有輸入管道。
2. **核心問題**：LLM 不會區分「指令」和「資料」，沒有像傳統資料庫那樣的「參數化查詢」可以把兩者徹底分開。[S1, 描述]
   → 與 S2「資料與指令界線模糊」一致。
3. **讓風險變大的三個部署因素** [S1, 描述]：
   - 所有內容混在同一個上下文視窗，沒有強制的信任邊界
   - 記憶會保留：一次注入可能影響之後的對話
   - Agent 執行：模型的輸出會驅動工具
4. **範圍**（新增）：直接輸入；網頁、文件、Email、RAG 段落；工具輸出與工具連線管道（如 MCP 伺服器）；圖片、聲音、影片；中間推理；長期記憶與 RAG 資料庫。內容不必人眼可見。[S1, 範圍]
5. **越獄**：越獄是 Prompt Injection 的子集，攻擊目標是讓模型違反安全規範。[S1, 越獄]（2026 版**維持** 2025 版的立場）
6. **類型** [S1, 類型]：
   - 直接注入：使用者（或掌握使用者管道的人）提供的輸入改變行為；可能故意（原文舉例：惡意使用者設計越獄），也可能無心（例如貼上了互相衝突的指示）。（2026-11-23 獨立複查後補記）
   - 間接注入：模型讀取的外部內容中藏有使用者沒寫、也沒看到的指令。依來源可信度分三層：
     - 不可信：公開網頁、陌生寄件者、搜尋結果
     - 半可信：公開問題回報系統、套件說明文件、第三方 API 回應
     - 可信：開發者自己的程式庫、資料庫、內部文件——但攻擊者可能從其他上游管道間接碰到
   - **新興模式**：攻擊者從低權限管道送入文字，讓**使用者自己的 Agent** 用使用者的高權限去執行。
7. **影響** [S1, 影響]：洩漏敏感資料或系統提示；輸出被操縱且被下游採用；未授權使用 Agent 工具，甚至執行破壞性操作；透過圖片網址、隱藏字元等方式外洩資料；透過記憶或 RAG 污染**跨對話持續**受控。
8. **防禦現況**：條目明言目前**沒有可靠的預防機制**；因此防禦應該從**架構**下手——假設指令邊界有時會被突破，限制模型能做什麼、輸出能觸及什麼。[S1, 防禦]
9. **致命三要素（lethal trifecta）**：條目引用 Simon Willison 提出的概念作為部署前檢查——同時具備「能存取私人資料」「會讀取不可信內容」「能對外溝通」三項時，風險最高；拿掉任一項，就消除高衝擊攻擊的條件。[S1, 防禦]
10. **十一項緩解策略**（每項都附上限制說明）[S1, 防禦#1–11]：

| # | 策略 | 白話 | 條目指出的限制 |
|---|---|---|---|
| 1 | 角色與能力限制 | 在系統提示中寫明能做／不能做什麼 | 只有部分效果，必須搭配權限控管 |
| 2 | 嚴格驗證輸出格式 | 用程式檢查輸出格式 | 抓不到語意上的操縱 |
| 3 | 多模態過濾 | 圖片、聲音也要過濾 | — |
| 4 | 憑證放在程式碼、最小權限 | 重要操作由程式把關，模型拿最少權限 | — |
| 5 | 移除隱藏字元 | 清掉看不見的 Unicode 字元 | 擋不住看得見的惡意文字 |
| 6 | 標示來源的管道 | 把外部內容標記出來，和指令分開 | 只在非適應性測試中有效 |
| 7 | 人工確認 | 重要、不可逆或對外的動作要人確認，並顯示確切內容 | — |
| 8 | 最多兩項規則（Rule of Two） | 不可信輸入（A）、敏感資料（B）、改變狀態或對外溝通（C）三者同時具備（[A,B,C]）時，每個動作都要人核准；**[A,B] 或 [A,C]** 兩項組合需明確評估剩餘風險（2026-11-23 獨立複查後補記） | — |
| 9 | 記憶寫入視為特權操作 | 寫入記憶前要檢查、記錄、核准 | — |
| 10 | MCP 與工具供應鏈控管 | 工具套件要固定版本、簽章、檢查說明文字 | 擋不住已存在於固定版本中的惡意內容 |
| 11 | 適應性攻擊測試 | 公開防禦設計後再請紅隊攻擊 | 只看靜態測試結果不夠 |

## 攻擊情境摘要（僅概念層級）[S1, 情境#1–9]

| # | 情境 | 可用於 |
|---|---|---|
| 1 | 客服機器人被使用者操縱，越權查資料、發訊息 | 直接注入 |
| 2 | 摘要網頁時觸發隱藏指令，透過輸出外洩對話 | 網頁風險 |
| 3 | 文件中嵌入的指示影響求職者用 AI 優化的內容，造成無心被標記 | 無心注入、生活化例子 |
| 4 | RAG 資料庫被投入文件，影響特定問題的回答 | RAG 風險 |
| 5 | 指令拆在多個欄位，單看都無害 | 偵測困難 |
| 6 | 指令藏在人眼看不出的圖片中 | 多模態 |
| 7 | **零點擊**：一封特製郵件讓助理在使用者沒操作的情況下外洩資料 | Email 風險、Agent 風險 |
| 8 | 有終端機權限的程式碼 Agent 被誘導執行破壞性指令 | Agent 工具風險 |
| 9 | 在 issue、工單或套件中放文字，讓開發者的 Agent 用高權限外洩程式碼或資料庫 | 新興模式、權限風險 |

| 項目 | 2025 版 | 2026 版 |
